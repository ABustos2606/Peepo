# Domain and engine contracts

**Implemented:** 13 October 2026. These contracts are used by the Windows editor and its deterministic simulated engine. The UI depends on `Engine`, rather than the concrete `SimulatedEngine`. They establish the adapter boundary. `IngenEngine` implements the same contracts over Ingen's protocol; where it differs from the simulator is recorded in [the adapter record](15-ingen-adapter.md).

## Identity and metadata

`InstanceId` identifies a module instance; plugin URI identifies its definition; the display name is independent of both. IDs are nonzero, unique in a graph, and not reused by ordinary add/duplicate operations. Duplicate copies parameters and software bypass into a new instance, leaving cables and control assignments with the original. Only the input/output endpoint definitions may be fixed; they cannot be deleted, moved, bypassed or duplicated.

Ports have logical symbols, input/output direction, explicit `PortType`, channel count and optional per-channel engine symbols. Each module can retain a port snapshot. This preserves a missing module's saved graph topology even when its definition cannot be resolved. Audio, Cv and Midi ports are cable endpoints; Control and Atom are represented in metadata but refused. Midi is an LV2 atom port that declares `atom:supports midi:MidiEvent`; Atom is any other atom port, such as the one a Cabinet or NAM takes its file on (split 20 October 2026, P12.4). A module may have several audio ports per direction; each is a separate jack and a `Connection` names both port symbols. Entries generated from upstream LV2 metadata are flagged `reference` and supply explicit channel symbols.

Parameters are tagged Continuous, Integer, Toggle or Enumeration. The canonical numeric payload is a `double`; discrete tags require exact integral values, bounded to integers representable exactly by that payload. Toggles have range 0–1; enumeration values are zero-based indices into their choices. Ranges, values and logarithmic minima must be finite and valid. Symbols are unique per module. Domain validation runs before an externally loaded graph replaces the active graph; rejected commands retain the previous state.

Catalogue availability is explicit: Available, Untested or Unavailable, with a reason for disabled entries. All available entries in this build are labelled demo entries. A missing definition remains a movable/removable placeholder with retained settings. Parameter/bypass/duplicate/new-cable commands for unavailable instances fail; their existing logical cables are retained but have no active routing plan.

## Cables

Revised 13 October 2026 at the user's request: free patching, connector by connector, as on Beebo.

`Connection` is one cable between one output port and one input port, named by module ID and port symbol. Every audio port in the catalogue is a single channel, so a cable is exactly one engine connection; a stereo module simply has two input ports and two output ports. Demo fixtures name them `in` / `in_r` and `out` / `out_r`; entries generated from LV2 metadata keep the plugin's own symbols (for example `l_in`, `r_in`). Moving or panning never alters routing.

Control (CV) ports are cabled the same way, one `Connection` per cable. A cable joins two ports of the same type: audio to audio, control to control or MIDI to MIDI; anything else is refused, as are scalar-control and message (Atom) ports.

MIDI cables (20 October 2026, revising D16) follow the same rules: several may leave an output and enter an input (Ingen merges event sequences in time order), no duplicates, no feedback cycles; the cycle check counts every cable type together. IN has a MIDI output `midi` and OUT a MIDI input `midi`, which are the engine graph's `midi_in` and `midi_out`: atom sequence ports supporting `midi:MidiEvent`, which Ingen's JACK driver turns into JACK MIDI ports. The adapter creates them on connect, as it does `in_l`…`out_r`; a saved patch writes and reads them like the audio endpoints. Ingen's own `control` and `notify` ports (the graph's first two, used by its MIDI-learn bindings) are not shown. Ingen's own rule (`ArcImpl::can_connect`) is looser and accepts audio, CV and control into each other.

Any audio output may feed any audio input, several cables may leave one output, and several may enter one input (the engine sums them at unity; see [engine evidence](14-ingen-engine-evidence.md)). The older multi-channel port fields and `expand_connection` remain in the model and its tests but no catalogue entry uses more than one channel per port.

Graph validation enforces endpoint identity, unique module/parameter/port symbols, finite typed values, assignment ranges, existing cable endpoints, direction/type/channel compatibility, no duplicate logical cables and no feedback cycles. Missing modules' retained ports allow an incomplete graph to be restored for repair. New connections to them remain disabled.

Fan-out and fan-in need no special cable type. `parallel_demo_graph()` supplies ten cables (five per side), with Drive feeding Clouds and Delay and both feeding OUT. Removing one cable leaves every other one intact. This fixture demonstrates graph routing, not a verified audio summing policy.

## Lifecycle and commands

`Engine::connect()` and `disconnect()` operate the connection lifecycle. The simulator normally starts Ready; reconnect passes through Connecting for 100 ms. Commands submitted outside Ready receive a correlated failure and are never queued for later application. Disconnect/error cancels queued edits and emits correlated failures, then a state/snapshot event. Reconnect keeps the last accepted graph and never applies cancelled edits.

`submit(Command)` returns a request ID. `advance(milliseconds)` drains events; each command result has its ID, accepted/failure state, message, current engine state and authoritative graph snapshot. State changes and simulated external graph replacements use request ID zero. The application tracks pending IDs, commits snapshots rather than optimistic mutations, and defers widget rebuilds until input gestures end.

Commands cover add, remove, move, duplicate, parameter, software bypass, connect/disconnect ports, load an external graph, create, rename, save and restore a session snapshot, and save and load a patch on disk. New patch creates fixed IN/OUT with a direct cable and a dirty marker. The UI guards replacement of unsaved edits and waits for pending work. Create/rename names reject blanks/control characters and are bounded; newly typed names are limited to 48 characters and the domain accepts at most 96 UTF-8 bytes. Rename preserves an existing backend name longer than 48 characters until the user edits it, rather than silently truncating it.

`SaveGraph` specifies Session or Persistent scope and whether plugin state is requested. Session save runs through the same delayed/rejectable engine command path, retains one in-memory graph snapshot, and clears the active graph's dirty marker only after success. `LoadSession` restores that snapshot, which survives new-patch creation and reconnect during the process. Engine events return the saved graph for UI preview. Closing the process clears it. A rejected save changes neither the saved snapshot nor dirty state.

`Assign` pins a physical control to a parameter or a module's bypass and `Unassign` clears it (14 October 2026). Assignments are part of the patch: they are validated against the parameter's range, replaced per control, removed with their module, and saved and loaded with everything else. One whose module is gone or holds another plugin is kept as an orphan, which `validate_graph` accepts and nothing applies; see [physical controls](18-physical-controls.md).

Persistent `SaveGraph` (revised 14 October 2026) names a bundle location as the engine sees it and the stored identity. The engine writes the graph there; the identity becomes `Graph::patch_id` and the dirty marker clears only after the engine answers. `LoadPatch` replaces the graph with a saved bundle and lists the blocks it should produce, so that a plugin the engine lacks is refused before anything changes and blocks the engine did not build are reported. Publishing revisions is the patch store's job, not the engine's. See [patch storage](17-patch-storage.md).

`EngineCapabilities` reports simulation, session save, persistent save, plugin-state capture and audio processing. The simulator supports the first three: its persistent save writes `main.ttl` and `manifest.ttl` in the engine's layout, and plugin-state requests return explicit unsupported-capability failures. The Ingen adapter supports persistent save and plugin state. Optional simulation controls default to unsupported in the abstract interface; the simulator implements error/rejection/missing-module fixtures for development.

`Engine::telemetry()` supplies optional global tempo (BPM) and CPU percentage independently of patch snapshots or module selection; its default is unknown for both. The simulator provides fixed display fixtures: 120 BPM and 12% CPU while Ready. CPU becomes unknown when disconnected, connecting or in error; the tempo fixture is retained across patch changes. This does not implement a musical clock, tempo propagation, MIDI sync or processor measurement. The footer displays unknown/non-finite/out-of-range CPU readings and non-positive tempo as `--`; load at 85% or above uses a warning color. Real adapters must supply fresh readings with a documented CPU measurement scope and source.

Real adapters must map these contracts to the verified protocol, provide their actual catalogue/port metadata, marshal I/O off the LVGL thread, and bound event queues. `IngenEngine` does this, with request timeouts and resynchronization after a reconnect; `register_definitions()` adds catalogue entries an adapter can vouch for, and `replace_catalogue()` offers exactly an exported catalogue, keeping only the IN and OUT endpoints. A definition may name the plugin's own on/off control (`enable_symbol`); the adapter then switches the module on when adding it and maps software bypass to that control. Its differences from the simulator: a lost engine is retried and shown as Connecting, not Disconnected; the session snapshot is held by the interface; the dirty marker and the stored identity are properties of the engine's graph, so a restarted interface finds them; tempo is unknown; and the simulation controls are unsupported.
